# Gallop v1.2 Real Tutor Integration

Status: **transport + controlled real four-Tutor learner dogfood complete**

Gallop exposes one headless STDIO MCP server per Tutor subject. The four server processes share one learner Journal/application while each launch is bound to exactly one subject:

| Server | Subject | Tutor ID |
|---|---|---|
| `gallop-mathematics-tutor` | `mathematics` | `mathematics-tutor` |
| `gallop-statistics-tutor` | `statistics` | `statistics-econometrics-tutor` |
| `gallop-finance-tutor` | `finance` | `finance-tutor` |
| `gallop-cs-ai-tutor` | `cs-ai` | `cs-ai-tutor` |

The subject is a process-level binding, not a caller-controlled field. A write whose event subject, Tutor ID, or recorder differs from that binding fails before Journal mutation. The transport uses the Python MCP SDK, contains no model call, has no DeepTutor dependency, and provides no separate learner UI.

## Tool surface

- `get_runtime_status` verifies configuration/Vault/Reader readiness without opening or initializing the Journal.
- `open_or_resume_session` commits/recovers session lifecycle and returns bounded Journal-derived context.
- `get_learning_context` and `get_session` are read-only.
- `record_learning_event` appends a validated Tutor event.
- `checkpoint_session` records meaningful incremental durability points.
- `finalize_session` records lifecycle completion without pretending finalization is the only durability boundary.

MCP metadata marks reads and writes explicitly. Server instructions require stable IDs, incremental checkpoints, candidate-only Tutor assessment, configured human/authority confirmation, and No-Agent Coding boundaries.

## Real learner configuration boundary

A real learner configuration must identify:

1. a private Gallop runtime/Journal root outside cloud storage;
2. the existing Obsidian Vault;
3. the existing `Gallop-Reader` target;
4. a separate export-state directory;
5. the validated Reader/cloud binding expected by the current machine.

The Journal is authoritative. Obsidian and Reader are projections. Synthetic events are rejected from learner authority state.

Do not repoint a previously bound runtime, recreate a Reader, reset export receipts, or repair cloud/provider state merely to make a gate pass.

## Write sequence

The durability sequence is:

```text
validate bound subject + Tutor identity + event schema
  → append Journal event atomically
  → rebuild/replay affected state
  → refresh Gallop-owned Obsidian projections
  → publish/refresh Reader when requested by the configured flow
  → return structured result
```

If the Journal commit succeeds but a projection step fails, the event remains committed and recoverable. A retry must preserve event identity rather than create a second learning event.

## Fresh-chat and restart behavior

`open_or_resume_session` derives continuity from the Journal, not from hidden chat transcript access.

Controlled acceptance demonstrated:

- intentional desktop/process termination while a Mathematics session remained active;
- restart with `created=false` and reconstruction of the committed session/evidence/checkpoints;
- later fresh chat receiving only the stable Mathematics session ID;
- independent retest evidence landing back in the original Journal without access to the old transcript.

A restore failure must be explicit and must not fabricate context or silently rewrite the committed session.

## Idempotency

Stable event identity is mandatory:

- byte/semantic-equivalent retry under the same normalized event identity → duplicate/no-op semantics;
- same identity with conflicting content → reject;
- duplicate confirmation must not create duplicate evidence authority;
- projection retries must not create additional Journal evidence.

Real dogfood verified duplicate recovery and zero duplicate projection writes after stable recovery.

## Projection and Reader safety

Real acceptance exercised normal projection plus a deliberate managed-note recovery case. When a fully Gallop-managed projection region/path was removed, projection failed closed instead of silently assuming deletion was accidental. The verified backup was restored and the Journal/derived state remained unchanged.

Reader publication is one-way. The phone/mobile Reader is not allowed to become an authority source for Vault/Journal mutation.

## Evidence authority

Tutor assessments remain candidate evidence. Real learner authorship/confirmation signals and evidence classification are recorded separately; they do not grant correctness by assertion alone.

Assisted evidence stays assisted. In the real Mathematics path, an assisted repair passed while the later independent retest was only `PARTIAL`; Gallop correctly retained `GUIDED`, mastery `0`.

Finance and CS/AI real dogfood produced accepted independent evidence under their recorded assistance/agent-use conditions. This demonstrates authority semantics, not general educational validity.

## Daily-use rule

Once runtime status, Vault ownership, and Reader binding are healthy, the user should study through the Tutor conversations rather than manually driving Gallop internals. CLI/manual tooling is for inspection, compatibility, testing, and recovery—not the normal learner UX.

## What this does not prove

This integration does not prove universal provider compatibility, psychometric validity, hostile-owner tamper resistance, perfect cloud atomicity, or that every Tutor judgement is correct. Those remain outside the claim.
