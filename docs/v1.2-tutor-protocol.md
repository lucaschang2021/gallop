# Gallop v1.2 Tutor Protocol

Status: **implemented and accepted through controlled real four-Tutor dogfood**

Version: `1.2`

Gallop v1.2 defines one bidirectional protocol for four permanent Tutor surfaces:

| Subject | Stable Tutor ID |
|---|---|
| Mathematics | `mathematics-tutor` |
| Statistics & Econometrics | `statistics-econometrics-tutor` |
| Finance | `finance-tutor` |
| CS & AI | `cs-ai-tutor` |

They are four policies over one Gallop system, not four backends. Gallop remains headless. The protocol requires neither DeepTutor nor a learner dashboard.

## Tutor → Gallop

The normative schema is [`tutor-event-v1.2.schema.json`](../gallop/schemas/tutor-event-v1.2.schema.json).

Every event carries:

- stable event/session/Tutor identity;
- one of the four subjects;
- explicit timezone-bearing occurrence time;
- bounded structured payload;
- learning-scoped provenance.

Supported event types are:

`session_start`, `context_request`, `concept_exposed`, `task_issued`, `learner_attempt`, `hint_given`, `feedback_given`, `candidate_assessment`, `evidence_confirmation`, `mistake_observed`, `prerequisite_issue`, `repair_attempt`, `reconstruction_attempt`, `independent_success`, `oral_response`, `proof_submission`, `coding_submission`, `simulation_result`, `paper_activity`, `checkpoint`, `session_idle`, and `session_finalize`.

The schema requires task/attempt/concept/response/evidence references where the event type needs them. Unknown top-level payload fields are rejected so a whole transcript, credential, or unrelated personal material cannot be silently attached. Large artifacts stay external and are referenced rather than embedded.

`session_finalize` is a lifecycle observation, not the sole durability boundary. Meaningful learning work should be checkpointed incrementally using stable event IDs.

## Gallop → Tutor

The normative schema is [`tutor-directive-v1.2.schema.json`](../gallop/schemas/tutor-directive-v1.2.schema.json).

Directives carry stable directive/session IDs, subject, issuance time, source Journal event IDs, and explicit `ADVISORY` authority.

Supported directive types are:

`learning_context`, `training_zone`, `scaffold_level`, `target_capability`, `prerequisite_focus`, `task_type`, `review_due`, `retest_due`, `independence_requirement`, `assessment_boundary`, `next_action`, and `unfinished_work`.

A target capability is never a statement about current capability. Gallop communicates policy/context; the Tutor still chooses explanations, wording, examples, and pedagogical interaction.

## Subject binding

The real transport launches one STDIO MCP server per subject. Subject identity is fixed at process launch, not chosen by each tool call. Before Journal mutation, Gallop checks that event subject, Tutor ID, and recorder identity match the bound server.

This prevents a Finance Tutor call from writing Mathematics evidence and is part of the security/authority boundary, not merely a UI convention.

## Authority and evidence safety

Tutor assessments are `CANDIDATE_EVIDENCE`. The protocol has no Tutor-originated `MASTERED` authority.

An `evidence_confirmation` must satisfy the configured human/attestation boundary and reference an existing candidate. Confirmation creates a distinct record; it never rewrites the candidate in place. Exact retries are idempotent by event ID.

Independence classification is constrained by actual assistance:

- nonzero assistance contradicts fully independent performance where the policy requires zero assistance;
- AI-generated work cannot be independent coding evidence;
- solution-seen / reference-only evidence stays weaker than closed-book independent evidence;
- a target or Tutor claim cannot promote current capability by itself.

These checks are enforced before evidence is admitted into authoritative progression state.

## Stable identity and retries

IDs are caller-supplied bounded tokens and act as idempotency keys:

- exact same ID + normalized content → duplicate/no-op semantics;
- same ID + different normalized content → conflict;
- process restart → rebuild from committed Journal events;
- fresh chat → restore from stable session identity, not transcript inference.

The protocol does not derive identity from chat text.

## Runtime Bridge

The transport-neutral Runtime Bridge validates lifecycle events and appends them to the existing Journal/application boundary. Candidate assessments and independent-success claims map into the existing evidence model without granting unsupported authority.

After a durable event commit, Gallop refreshes privacy-filtered owned projections for the affected subject. Projection is downstream of Journal authority: if projection fails, the committed event remains durable and recoverable.

## Context Builder

The Context Builder returns deterministic, bounded advisory context from replayed Journal state only. It can include:

- current vs target capability;
- active concepts and unfinished work;
- recent evidence with authority/assistance distinctions;
- known mistakes and prerequisite issues;
- reviews/retests due;
- scaffolding/training-zone guidance;
- next action.

It does not load the old chat transcript as authority and does not read arbitrary Vault prose into state. Private references are filtered. A stable Journal head produces stable context/directive content.

## Fresh-chat continuity

`open_or_resume_session` returns context automatically. If a previous session was interrupted, the bridge reconstructs it from Journal history after process restart. A new chat can continue using only the stable session identity.

A restore failure must not fabricate context or roll back an already committed session start. Failure is explicit and recoverable.

## Validation and acceptance

Validation now has three layers:

1. **protocol/unit validation** — schema, authority, cross-subject rejection, idempotency;
2. **isolated Four-Subject Golden E2E** — proof, simulation/inference, derivation, No-Agent Coding, delayed retest, fresh-chat continuity over one Journal;
3. **controlled real dogfood** — actual learner interactions across all four Tutors, abrupt-close recovery, duplicate recovery, owned Obsidian projection, Reader recovery/publication, and mobile visibility.

The real acceptance record is [`audits/v1.2-real-dogfood-acceptance.md`](audits/v1.2-real-dogfood-acceptance.md). Acceptance deliberately preserved a partial Mathematics retest as `GUIDED`, mastery `0`, demonstrating that runtime success does not require false learner promotion.

Synthetic examples for all four subjects remain under [`examples/tutor-protocol`](../examples/tutor-protocol/).
