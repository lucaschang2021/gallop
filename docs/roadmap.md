# Roadmap

Gallop has completed its v1.2 Zero-Touch architecture milestone and is now in a **sustained daily-use phase**. This roadmap distinguishes shipped capability, maintenance priorities, and explicitly deferred scope. It does not assign speculative version numbers or dates.

See [current status](current-status.md) for dated evidence and limitations.

## Shipped baselines

- **v0.1.0:** structured session/practice protocols, Obsidian/Markdown adapter, external DeepTutor boundary, conservative legacy mastery, replay-safe result import, review entries, and an isolated synthetic demo.
- **v1.0.0 / Automation V1:** raw intake, append-only events, deterministic replay, four-subject queues, human-confirmed practice/assessment, mastery safety rules, durable DeepTutor jobs, owned Obsidian projections, and filtered Gallop-Reader publication.
- **v1.1 governance / Progressive Mentorship:** evidence-aware readiness, target capability, prerequisite links, struggle/scaffolding logic, pure progression domain, executable architecture governance, exact V1 replay protection, and stronger privacy/type/lint gates.
- **v1.2 Zero-Touch Learning Continuity:** four subject-bound GPT Tutor MCP servers, versioned Tutor Protocol, Runtime Bridge, incremental checkpoints, bounded Journal-derived context, fresh-chat restore, automatic Tutor projections, real four-Tutor dogfood, abrupt-close recovery, duplicate recovery, and mobile-visible one-way Reader continuity.

These milestones establish executable learning-governance workflows. They do **not** establish general learning efficacy, psychometric validity, or autonomous grading authority.

## Current phase: USE

The default operating priority is now:

1. use Gallop every day in the four Tutor surfaces;
2. accumulate real learning evidence across courses and semesters;
3. watch for continuity, projection, evidence-authority, and recovery regressions;
4. make only evidence-backed corrective changes;
5. keep architecture frozen unless sustained real use demonstrates a missing primitive.

A new feature is not automatically valuable because it is technically possible. v1.2 should remain small, understandable, replayable, and trustworthy.

## Near-term maintenance priorities

| Priority | Work | Completion evidence |
|---|---|---|
| Daily-use reliability | Exercise all four Tutors across normal study sessions, fresh chats, restarts, delayed reviews, and longer histories | No evidence loss, cross-subject leakage, unsupported promotion, or unrecoverable projection drift |
| Evidence calibration | Expand real subject-specific examples of independent, assisted, partial, failed, oral, proof, coding, simulation, and research evidence | Weak evidence remains weak; assistance boundaries stay conservative; replay semantics remain stable |
| Context quality | Observe bounded context usefulness as Journal history grows | Tutors receive enough current/unfinished/prerequisite context without transcript dumping or private-data expansion |
| Projection durability | Continue PC/Vault/Reader recovery checks under ordinary Obsidian/cloud behavior | Journal authority survives projection/cloud interruptions; managed ownership remains fail-closed |
| Release reproducibility | Keep version/source/tag/release facts separate; improve repeatable build/install evidence | Clean-environment install and offline checks from an explicitly identified source/tag/artifact |
| Contributor clarity | Keep bilingual entry docs, architecture, protocol, and examples aligned | Fresh-clone developer can understand authority boundaries and reproduce public checks without private learner data |

## Changes allowed without a new architecture phase

Small maintenance changes are expected when backed by observed failures:

- bug fixes;
- clearer Tutor instructions or schema rejection messages that preserve semantics;
- additional tests for an already-defined invariant;
- safer recovery behavior;
- documentation corrections;
- bounded performance improvements that do not change authority;
- additional subject fixtures inside the existing four-subject contract.

Any change to event meaning, replay rules, mastery authority, identity, persistent format, or subject isolation requires explicit migration/compatibility analysis.

## Deferred scope

The following are **not** part of v1.2 and should not be started merely because the base system is complete:

- Competition Mathematics / Yau specialization;
- autonomous adaptive curriculum expansion beyond the governed mentorship contract;
- general semantic retrieval / embedding infrastructure;
- a broad plugin marketplace or agent ecosystem;
- a separate Gallop frontend/dashboard;
- automatic proctoring or identity verification;
- automatic replacement of human evidence authority;
- provider-specific coupling in the core architecture.

These may be reconsidered only when real usage produces a concrete requirement that cannot be met cleanly by the current primitives.

## Enduring constraints

- Automate learning operations, never fabricate learner work or assessment.
- Preserve local ownership and explicit migration decisions.
- Journal is authoritative; GPT and Obsidian are not.
- Keep synthetic validation isolated from real learner evidence.
- Targets never raise current capability.
- Assistance never masquerades as independence.
- Keep the four Tutors as one governed Gallop system, not four divergent backends.
- Prefer reproducible evidence and small interfaces over feature count.

## Stop rule

If daily use is stable, **do not invent another development milestone**. Gallop succeeds when it disappears under the learning workflow and reliably preserves evidence, continuity, and training direction.
